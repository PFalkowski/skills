# Immich under the OMV Compose plugin

Immich is a self-hosted photo library. On an OMV box the interesting part is not Immich,
it is *who owns the compose file*.

## Use the OMV Compose plugin, and know what it does

Install `openmediavault-compose` from omv-extras, then add Immich as a compose file through
**Services → Compose → Files**. OMV then writes and manages the deployment for you:

```
/appdata/immich/
├── immich.yml            <- generated by OMV. "Do not edit, your changes will get lost."
├── immich.env            <- your variables (UPLOAD_LOCATION, DB_*, …)
├── compose.yml  -> immich.yml
└── .env         -> immich.env
```

The header OMV writes into that file is not decoration:

```yaml
# This file is auto-generated by openmediavault (...)
# WARNING: Do not edit this file, your changes will get lost.
```

**Edit the compose through the OMV UI, never on disk.** A hand edit survives until the next
apply and then vanishes, which produces the worst class of bug: a config that worked
yesterday, no diff explaining why it stopped, and a service that is now running something
you did not write. If you need something OMV's field cannot express, use
`compose.override.yml`, which the plugin leaves for exactly this.

Note the symlink pair. `docker compose` looks for `compose.yml` and `.env`; OMV names its
files after the stack and links them. Follow the links before concluding a file is missing.

## Track upstream's compose, do not write your own

Immich ships a compose file per release and explicitly warns that `main` may not match the
latest release. Take theirs:

```
https://github.com/immich-app/immich/releases/latest/download/docker-compose.yml
```

Four services, not two — this is the most common thing a hand-written file gets wrong:

| Service | Notes |
|---|---|
| `immich-server` | the app; publishes `2283` |
| `immich-machine-learning` | search, face and object recognition. **Omitting it silently disables those features** rather than failing |
| `database` | a *purpose-built* Postgres image with the vector extension Immich needs — not stock Postgres, and not interchangeable |
| `redis` | now a Valkey image upstream, not `redis:*` |

Two more details upstream sets that hand-written files usually miss: `shm_size: 128mb` on
the database, and `POSTGRES_INITDB_ARGS: '--data-checksums'`. The second only takes effect
at *initialisation* — setting it after the cluster exists does nothing, and fixing it later
means a dump and restore.

Upstream pins the database and redis images **by digest**. Keep the digests. A photo library
whose vector extension changes version underneath it is not a pleasant afternoon.

Do not copy a `version:` key from an old example. Compose v2 ignores it and warns; upstream
uses a `name:` key instead.

## Storage

Point `UPLOAD_LOCATION` and `DB_DATA_LOCATION` at the data disk, not the OS disk:

```
UPLOAD_LOCATION=/srv/dev-disk-by-uuid-<DISK_UUID>/immich/upload
DB_DATA_LOCATION=/srv/dev-disk-by-uuid-<DISK_UUID>/immich/postgres
```

The database directory must be a real local filesystem path. Putting a Postgres data
directory on a network share (SMB/NFS) corrupts it — the locking semantics are not there.

Keep `immich.env` at mode `0600`. It contains the database password.

## Access from a phone

Publish nothing to the internet. `tailscale serve` gives Immich a real HTTPS URL that only
your tailnet can reach — see [REMOTE.md](REMOTE.md):

```bash
tailscale serve --bg 2283
# https://<NAS_TS_NAME>.<TAILNET>.ts.net  ->  127.0.0.1:2283
```

Put that URL into the Immich mobile app as the server address. Background photo backup then
works over mobile data with no port forwarding and no certificate warnings.

## Backups

Snapshotting the upload directory is not a backup of the library — the database holds
albums, faces, and all metadata. Back up both, and dump the database rather than copying
its files while it runs:

```bash
BACKUP_ROOT=/srv/dev-disk-by-uuid-<DISK_UUID>
dump="$BACKUP_ROOT/backups/immich-$(date +%F).sql.gz"

# The destination is removable, and an unmounted mount point is an ordinary directory.
# Without this the backup writes itself onto the OS disk it exists to protect.
mountpoint -q "$BACKUP_ROOT" || { echo "backup disk detached" >&2; exit 1; }

# No -t. A pty rewrites every LF as CRLF - including inside the COPY ... FROM stdin
# blocks, whose lines are read literally on restore - and folds stderr into the archive.
# Opening the redirect also creates the file whether or not the dump works, so write
# under .partial and rename only once the completion trailer proves it ran to the end.
docker exec immich_postgres pg_dumpall --clean --if-exists -U "$DB_USERNAME" \
  | gzip > "$dump.partial"
gzip -t "$dump.partial" \
  && gzip -dc "$dump.partial" | tail -5 | grep -q 'database cluster dump complete' \
  || { echo "dump incomplete" >&2; rm -f "$dump.partial"; exit 1; }
mv "$dump.partial" "$dump"
```

Check the trailer rather than a minimum size: an empty input compresses to a perfectly
valid 20-byte gzip that `gzip -t` accepts, and a size floor large enough to catch that will
also fail shut on a freshly restored cluster that is legitimately small.

Whatever prunes old dumps must run *after* a successful one, or a fortnight of failures
takes the last good copy with it. If the library is mirrored with `rsync --delete`, guard
the source the same way: "empty because its disk went away" is a deletion, and `--delete`
will propagate it.

**Restore, and test it.** A dump nobody has restored is a hypothesis. Dumps taken with the
old `-t` need their line endings stripped on the way in:

```bash
gzip -dc immich-<date>.sql.gz | tr -d '\r' | docker exec -i immich_postgres psql -U postgres
```

Both guards are there because both have fired on a real box. Whatever prunes old dumps must
run *after* a successful one, or a fortnight of failures takes the last good copy with it.
And if the library is mirrored with `rsync --delete`, guard the source the same way: "empty
because its disk went away" is a deletion, and `--delete` will propagate it.

## Script

```bash
scripts/40-immich.sh --check   # plugin installed? all four services up? data on the right disk?
                               # env mode 0600? serve configured? digests pinned?
```

It reports; it does not deploy. Deployment goes through the OMV UI, for the ownership
reason at the top of this file.
